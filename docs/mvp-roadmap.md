# MarginPilot — نقشهٔ راه اجرایی MVP

**وضعیت سند:** مصوب کاربر در ۲۰۲۶-۱۱-۲۰  
**مبنای کد:** `phase4-step4-release`، commit `ec2491f6dfb39cee8b50d98994fb0b126bfc2883`  
**هدف:** رساندن سریع MarginPilot به یک Mini-SaaS قابل استفاده و عرضه برای کسب‌وکارهای کوچک، با حفظ صحت مالی و امنیت داده؛ بدون ساخت زیرساخت سازمانی پیش از اثبات نیاز.

---

## ۱. تصمیم محصول و اصل اجرایی

MarginPilot باید در کوتاه‌ترین مسیر قابل دفاع به این خروجی برسد:

1. کاربر بتواند کالاها و تأمین‌کنندگان را ثبت یا از Excel/CSV وارد کند.
2. قیمت‌های خرید تأمین‌کنندگان را ثبت و با هم مقایسه کند.
3. فروش‌ها و هزینه‌های مرتبط را ثبت یا وارد کند.
4. سود واقعی هر کالا و عملکرد کلی کسب‌وکار را ببیند.
5. گزارش قابل استفاده برای تصمیم‌گیری دریافت کند.

**اصل راهنما:** فقط قابلیت، abstraction، سرویس یا زیرساختی ساخته شود که برای MVP مصرف‌کنندهٔ روشن دارد یا برای امنیت، صحت مالی و پایداری حداقلی ضروری است. طراحی آینده‌نگر نباید به پیاده‌سازی زودهنگام قابلیت‌های استفاده‌نشده تبدیل شود.

## ۲. وضعیت واقعی پروژه در نقطهٔ شروع این نقشه

| حوزه | وضعیت مستند |
|---|---|
| زیرساخت، CI و استقرار محلی | پیاده‌سازی شده؛ وضعیت و شواهد در اسناد Phase 2 و CI ثبت شده |
| Authentication، نشست امن، tenancy و RBAC | پیاده‌سازی و تست شده در Phase 3 |
| کاتالوگ کالا، واریانت، دسته، تأمین‌کننده و لیست قیمت | پیاده‌سازی شده در Phase 4 Step 1–2 |
| Import کالا و قیمت تأمین‌کننده | پیاده‌سازی و در CI منتشر شده در Phase 4 Step 3 |
| موتور مقایسهٔ قیمت تأمین‌کنندگان | API/backend پیاده‌سازی و در CI منتشر شده در Phase 4 Step 4؛ رابط کاربری و خروجی Excel آن هنوز تحویل نشده |
| فروش، مرجوعی و هزینه‌ها | قرارداد و طراحی در اسناد دامنه وجود دارد؛ persistence و قابلیت اجرایی هنوز تحویل نشده |
| محاسبهٔ سود واقعی و قیمت پیشنهادی | اصول و بردارهای مرجع طراحی شده‌اند؛ موتور اجرایی هنوز تحویل نشده |
| داشبورد، تحلیل و گزارش PDF/XLSX | در حد طراحی/قرارداد؛ قابلیت اجرایی MVP هنوز تحویل نشده |

**قاعدهٔ شواهد:** وجود پوشهٔ ماژول، قرارداد API یا مدل طراحی‌شده به معنی پیاده‌سازی نیست. وضعیت «انجام‌شده» فقط پس از وجود کد اجرایی، تست مرتبط و شواهد CI اعلام می‌شود.

## ۳. فازبندی فشرده و مصوب

فازهای قبلی زیرساخت، هویت، tenancy/RBAC و کاتالوگ/Import/Comparison حفظ می‌شوند. ادامهٔ کار با چهار بستهٔ تحویل محصولی انجام می‌شود؛ این فازبندی جایگزین ریزفازبندی بیش‌ازحد است، نه بازنویسی تاریخچهٔ فازهای انجام‌شده.

### Phase 5 — Sales & Expenses

برنامهٔ اجرایی این فاز: [phase5-plan.md](phase5-plan.md).

**هدف:** ایجاد دادهٔ عملیاتی لازم برای محاسبهٔ سود.

**محدودهٔ ضروری**
- ثبت و مدیریت فروش و اقلام فروش با ارتباط tenant-safe به کالا/واریانت.
- ثبت مرجوعی و اثر آن بر مقدار/درآمد فروش، مطابق قراردادهای موجود.
- ثبت هزینه‌های مستقیم و مشترک کسب‌وکار و تعریف مبنای تخصیص هزینهٔ مشترک مطابق مدل مصوب.
- کنترل وضعیت اسناد، تاریخ‌ها، مقدار، واحد، ارز و قواعد جلوگیری از دادهٔ مالی ناسازگار.
- فعال‌سازی Sales import فقط پس از آماده‌شدن مدل فروش؛ حفظ الگوی دو مرحله‌ای validate → preview → confirm و idempotency.
- Audit، RBAC و tenant isolation برای همهٔ عملیات نوشتن.

**خارج از محدوده:** حسابداری دوبل، دفترکل عمومی، خزانه‌داری، انبارداری جامع، خرید/پرداخت کامل و گردش‌کار تأیید چندسطحی.

**معیار پذیرش**
- Migration قابل upgrade/downgrade/upgrade و بدون drift روی PostgreSQL واقعی.
- تست‌های integration برای فروش، اقلام، مرجوعی، هزینه‌ها، تخصیص و محدودیت tenant.
- تست Decimal و قواعد مالی؛ عدم استفاده از float.
- تست import فروش با rollback اتمیک، idempotency، ردیف‌های نامعتبر و گزارش خطا.
- CI سبز، مستندات API/data model به‌روز.

### Phase 6 — Financial Calculation Engine

**هدف:** تبدیل داده‌های فروش، مرجوعی، خرید و هزینه به سود قابل اتکا.

**محدودهٔ ضروری**
- پیاده‌سازی deterministic و نسخه‌دار اصول محاسبات مصوب در `calculation-principles.md`.
- محاسبهٔ درآمد خالص، بهای تمام‌شده، سود ناخالص/خالص و حاشیهٔ سود در سطح کالا و کسب‌وکار.
- اعمال مرجوعی و تخصیص هزینه‌های مستقیم/مشترک با قواعد صریح و قابل بازتولید.
- نگهداری provenance ورودی‌ها، زمان محاسبه و `formula_version` برای بازتولید نتایج.
- پیشنهاد قیمت فروش بر پایهٔ هزینه و حاشیهٔ هدف، با نمایش فرض‌ها؛ پیشنهاد نباید خودکار قیمت محصول را تغییر دهد.
- پوشش بردارهای مرجع مالی و موارد مرزی؛ هر تغییر فرمول با نسخه و تست مشخص.

**معیار پذیرش**
- تمام بردارهای مرجع مصوب و تست‌های مرزی پاس شوند.
- تکرار محاسبه با ورودی و نسخهٔ فرمول یکسان نتیجهٔ یکسان بدهد.
- جمع تخصیص‌ها با مبلغ مبدأ برابر باشد؛ rounding طبق سیاست مصوب.
- تست‌های مستقل برای صفر، مرجوعی کامل/جزئی، تخفیف، هزینهٔ مشترک و دادهٔ ناقص.
- هیچ محاسبهٔ مالی در Frontend انجام نشود.

### Phase 7 — MVP UI, Dashboard & Reports

**هدف:** قابل استفاده کردن قابلیت‌های Backend برای کاربر نهایی.

**اولویت تحویل**
1. مسیرهای اصلی کاربر: ورود، انتخاب کسب‌وکار، کالا/تأمین‌کننده، import، فروش/هزینه.
2. رابط مقایسهٔ قیمت تأمین‌کننده و نمایش موارد مبهم برای تصمیم صریح کاربر.
3. داشبورد ساده: فروش، سود، حاشیهٔ سود و کالاهای سودده/زیان‌ده؛ فقط شاخص‌هایی که تعریف محاسباتی و منبع معتبر دارند.
4. گزارش Excel و PDF برای خروجی‌های اصلی؛ خروجی CSV در صورت نیاز واقعی و با هزینهٔ پیاده‌سازی پایین.
5. خروجی Excel مقایسهٔ تأمین‌کنندگان در صورت تکمیل مسیر اصلی مقایسه.

**قاعدهٔ UX:** فارسی و RTL، وضعیت‌های loading/empty/error، صفحه‌بندی و فیلترهای ضروری؛ بدون report builder یا داشبورد سفارشی پیچیده.

**معیار پذیرش**
- کاربر بتواند جریان اصلی را بدون API دستی کامل کند.
- اعداد UI با خروجی موتور محاسبه و API یکسان باشند.
- فایل‌های خروجی از نظر فرمت، encoding، اعداد، فرمول‌های مخرب spreadsheet و tenant isolation تست شوند.
- تست‌های component و E2E برای جریان‌های حیاتی.

### Phase 8 — Release Readiness

**هدف:** آماده‌سازی نسخهٔ MVP برای استقرار کنترل‌شده و استفادهٔ واقعی.

**محدودهٔ ضروری**
- E2E جریان حیاتی از ایجاد/ورود tenant تا import، ثبت فروش/هزینه، مشاهدهٔ سود و دریافت گزارش.
- بازبینی امنیتی متمرکز بر ریسک‌های واقعی: احراز هویت، مجوزها، tenant isolation، upload، session/CSRF، secret و dependency scan.
- تست کارایی فقط برای مسیرهای پرتکرار و حجم‌های متناسب با مشتری اولیه؛ ثبت baseline و اصلاح گلوگاه‌های واقعی.
- مستند استقرار، پیکربندی محیط، migration و عملیات.
- backup و restore واقعی PostgreSQL با آزمون بازیابی و ثبت RPO/RTO هدف MVP.
- راهنمای حداقلی پشتیبانی و مشاهده‌پذیری خطاها.

**معیار پذیرش**
- CI کامل سبز و سناریوهای E2E حیاتی پاس.
- آزمون restore موفق و دادهٔ بازیابی‌شده قابل اعتبارسنجی.
- هیچ blocker امنیتی/مالی باز نماند.
- دستورالعمل استقرار از ابتدا تا health check قابل اجرا باشد.

## ۴. مواردی که عمداً به بعد از MVP موکول می‌شوند

- Microservices، چندریپویی یا معماری توزیع‌شده.
- Redis/Celery/صف پیچیده و پردازش پس‌زمینه، مگر آنکه محدودیت عملیاتی اندازه‌گیری‌شده آن را لازم کند.
- حسابداری کامل، دفترکل دوبل و ماژول‌های ERP.
- انبارداری جامع، چند انبار و گردش‌کارهای پیشرفته.
- گزارش‌ساز سفارشی و تحلیل‌های پیشرفته.
- AI برای تصمیم‌گیری مالی یا محاسبهٔ سود؛ محاسبات باید deterministic بمانند.
- اپلیکیشن موبایل، چندمنطقه‌ای و زیرساخت مقیاس سازمانی.
- بهینه‌سازی مقیاس پیش از مشاهدهٔ بار واقعی.

این موارد حذف دائمی نیستند؛ فقط تا زمان اثبات نیاز محصولی/عملیاتی وارد MVP نمی‌شوند.

## ۵. مواردی که قابل مصالحه نیستند

سرعت اجرا به معنی کاهش کیفیت پایه نیست. موارد زیر در همهٔ فازها الزامی‌اند:
- جداسازی tenant و کنترل دسترسی سمت Backend.
- دقت مالی با Decimal/NUMERIC و فرمول‌های مستند و نسخه‌دار.
- Migration امن و قابل بازگشت.
- تست PostgreSQL واقعی برای قیود و تراکنش‌ها؛ mock جایگزین آن نیست.
- اعتبارسنجی فایل و جلوگیری از import ناقص/تکراری.
- Audit برای عملیات حساس و مدیریت امن نشست.
- CI و dependency/secret scanning.
- backup و restore آزموده‌شده پیش از عرضهٔ عمومی.

## ۶. قواعد مدیریت دامنه و تحویل

1. هر فاز یک خروجی قابل استفاده و معیار پذیرش روشن دارد؛ از شکستن غیرضروری به چندین فاز ریز خودداری می‌شود.
2. طراحی موجود در `data-model.md` و `api-contract.md` نقطهٔ شروع است؛ پیش از کدنویسی، فقط شکاف‌ها و تناقض‌های لازم اصلاح می‌شوند، نه بازطراحی کامل.
3. هر تغییر schema ابتدا با migration و تست tenant-aware همراه می‌شود.
4. قابلیت‌های خارج از MVP بدون نیاز روشن وارد کد، dependency یا معماری نمی‌شوند.
5. هر فاز پس از تست، بازبینی مستقل، به‌روزرسانی مستندات و تأیید کاربر بسته می‌شود؛ سپس فاز بعد آغاز می‌شود.
6. انتشار به `main`، merge، PR، یا انتشار نسخه فقط با اجازهٔ صریح جداگانه انجام می‌شود.
7. سقف‌های فعلی import/comparison تا زمان اندازه‌گیری بار واقعی ثابت می‌مانند؛ پیش از افزایش concurrency باید رفتار حافظه، زمان تراکنش و قفل tenant اندازه‌گیری شود.

## ۷. تعریف موفقیت MVP

یک فروشگاه کوچک بتواند بدون ابزار توسعه‌دهنده:
- کاتالوگ و قیمت تأمین‌کنندگان خود را وارد کند؛
- قیمت‌ها را مقایسه کند؛
- فروش و هزینه را ثبت/وارد کند؛
- سود واقعی کالاها و کسب‌وکار را ببیند؛
- کالاهای زیان‌ده را تشخیص دهد؛
- گزارش قابل استفاده دریافت کند.

**معیار نهایی، تحویل این جریان کامل و قابل اعتماد است؛ نه تعداد فازها، تعداد سرویس‌ها یا پیچیدگی معماری.**
